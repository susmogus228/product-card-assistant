# Черновики B2B-карточек измерительных приборов

Локальная Python-утилита принимает JSON товара, обращается к Groq и сохраняет
черновик карточки в JSON и Markdown. Контент-менеджер получает SEO-заголовок,
описание, таблицу характеристик, поисковые запросы и блок для менеджера.

Два товара в `examples/products/` подобраны по официальным данным Testo.
Работодатель пока не предоставил свои исходные товары. Эти демонстрационные
примеры нужно заменить, когда появятся данные работодателя.

## Требования и установка

- Python 3.12 или новее.
- Аккаунт Groq и API-ключ для генерации. Модель по умолчанию: `openai/gpt-oss-120b`.
- Интернет нужен для установки пакетов и обращения к API.

PowerShell, из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m pip install -e . --no-deps
if (!(Test-Path -LiteralPath '.env')) { Copy-Item -LiteralPath '.env.example' -Destination '.env' }
```

Откройте `.env` в локальном редакторе и заполните `GROQ_API_KEY`. Ключ не добавляйте
в код или Git. Если `.env` уже существует, сохраните его и пропустите Copy-Item.
Переменные окружения имеют приоритет над `.env`. Программа читает `.env` только
из текущего каталога. Имя модели задаёт `GROQ_MODEL`.

На Linux/macOS используйте `python3` для создания окружения и `.venv/bin/python`
вместо `.\.venv\Scripts\python.exe`. В этой работе проверен запуск на Windows.

## Запуск

Один запрос к модели, два формата результата:

```powershell
.\.venv\Scripts\python.exe -m product_card examples/products/testo-905-t1.json --format both --output outputs/my-905
.\.venv\Scripts\python.exe -m product_card examples/products/testo-608-h1.json --format both --output outputs/my-608
```

Параметр `--output` для `both` задаёт префикс: первая команда создаст
`outputs/my-905.json` и `outputs/my-905.md`. Существующие файлы программа не заменяет;
для повторного запуска выберите новый префикс.

По умолчанию программа выводит JSON в stdout. Сообщения об ошибках и сохранении
пишет в stderr. Можно выбрать только Markdown:

```powershell
.\.venv\Scripts\python.exe -m product_card examples/products/testo-905-t1.json --format markdown --output outputs/my-card.md
```

После установки также доступна команда `.\.venv\Scripts\product-card.exe`.

## Входной JSON

Один UTF-8 файл содержит один объект:

```json
{
  "name": "Название прибора",
  "manufacturer": "Производитель",
  "specs": {
    "характеристика из паспорта": "исходное значение",
    "поле для уточнения": null
  },
  "description": "Описание или фрагмент технического паспорта"
}
```

Все текстовые значения должны быть строками либо `null`. В `specs` числовые
значения передавайте строками вместе с единицами. Пустые строки означают отсутствие
данных. Названия характеристик могут отличаться у разных приборов. Неизвестные
верхнеуровневые поля, повторяющиеся JSON-ключи, NaN, неверные типы и файлы больше
256 КиБ программа отклоняет до обращения к API.

## Результат и ограничения длины

- `seo_title`: 1-70 символов.
- `seo_description`: 800-1200 символов.
- `characteristics`: название, значение и источник каждой характеристики.
- `search_queries`: 3-5 различных запросов.
- `commercial`: аудитория и задачи прибора, до 600 символов; числовые характеристики
  и условия точности остаются в описании и таблице.
- `missing_fields`, `warnings`: пропуски, противоречия и необходимые уточнения.
- `evidence`: ссылки на поля входа для каждого блока текста.
- `validation`: длины строк, число запросов и прохождение автоматических проверок.
- `model`, `generation_attempts`: модель и число попыток генерации.

Длину считаем через Python `len` после удаления пробелов по краям: Unicode-символы,
включая внутренние пробелы и знаки препинания. Разметка Markdown в длину не входит.
`requirements_passed=true` означает прохождение автоматических проверок формы и
лексических ограничений. Это не подтверждение смысловой достоверности всех фраз.

Статус `draft` означает черновик для ручной проверки. При недостатке данных или
подтверждённом конфликте статус `needs_data`: программа сохраняет известные
характеристики, помечает пробелы и не выдаёт SEO-текст за соответствующий требованиям.
Полностью пустой ввод, отсутствие имени и отсутствие фактов для описания не вызывают API.

## Достоверность технических данных

1. Программа копирует заполненные значения `specs` в таблицу без пересчёта и округления.
2. Для новых характеристик из `description` модель возвращает точную цитату; программа
   проверяет, что значение входит в цитату, а цитата входит в исходное описание.
3. JSON Schema ограничивает ссылки `evidence` существующими ID полей этого товара.
4. Валидатор отклоняет новые числа, неподтверждённые сочетания числа с известной единицей
   и некоторые опасные технические утверждения: IP, Bluetooth, ATEX и другие.
5. Промпт требует сохранять условия погрешности, ограничения диапазона и длительности.
   Сведения о наличии, цене, гарантии и совместимости без источника запрещены.
6. Модель сообщает противоречия между `specs` и описанием; программа проверяет цитату и
   вместо спорной характеристики выводит «требует уточнения».
7. Если в описании есть короткие фразы без числовых характеристик и обещаний точности,
   модель выбирает commercial-блок из их точных сочетаний. Схема и локальная проверка
   запрещают добавлять новые области применения в этот блок. При отсутствии подходящих
   фрагментов действуют обычная генерация и проверки; результат требует ручной сверки.

Лексические проверки не доказывают, что утверждение следует из источника. Например,
они могут пропустить перестановку двух значений с одной единицей, отрицание или
неподтверждённую пригодность для среды. Список единиц и технических слов ограничен.
Модель также может не заметить конфликт. Перед публикацией человек сверяет тексты с
паспортом; для двух сохранённых демонстрационных результатов такая сверка входит в проверку.

Текст товара передаём как данные, отдельно от системного промпта. Простой фильтр известных
команд вроде `Ignore previous instructions` отправляет такой вход на ручное уточнение.
Он не заменяет полную защиту от всех форм prompt injection.

## Промпт и обработка ошибок

Системный промпт находится в `src/product_card/prompts.py`. Он задаёт роль, правила
достоверности, русский язык, формат ответа и короткие примеры: пропущенное поле,
извлечение по цитате, конфликт значений, погружение зонда, условие точности и вычисляемая
точка росы. Это few-shot prompting, без обучения весов модели. Последние три примера
проверены как экспериментальный промпт на одном товаре; преимущество перед прежней
версией не установлено, поэтому ручная проверка остаётся обязательной.
В пользовательском сообщении передаём товар, допустимые ID источников и коды ошибок
для единственной корректирующей генерации.

Используем строгий JSON Schema на стороне Groq и Pydantic на стороне приложения.
Верхние границы длины SEO-текстов задаём в схеме Groq и повторно проверяем локально;
минимум 800 символов для полного описания проверяем локально.
Пустое описание в схеме разрешено для недостаточных данных; полная карточка с ним
проверку не пройдёт. Если ответ не проходит проверки, делаем ещё одну
генерацию. После второй неудачи возвращаем ошибку и не сохраняем непроверенную карточку.

У сетевого клиента таймаут 30 секунд и один автоматический повтор для временных ошибок.
Итого максимум две попытки генерации, каждая может содержать до двух HTTP-попыток.
Задержка по `Retry-After` может увеличить длительность команды. Ошибки авторизации,
квоты, соединения, таймаута и ответа модели выводим без сырых тел запросов и ключа.

| Код завершения | Значение |
| --- | --- |
| 0 | Черновик прошёл автоматические проверки |
| 2 | Ошибка входа, пути, конфигурации или существующий выходной файл |
| 3 | Ошибка API либо ответ модели не прошёл проверки после исправления |
| 4 | Нужны данные или ручное уточнение; результат содержит `needs_data` |

Groq Free имеет квоты. При их исчерпании дождитесь восстановления лимита и повторите
команду с новым именем результата. Программа не переключает тариф и не подключает оплату.
Фактические лимиты аккаунта смотрите в консоли Groq.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check src tests
```

Автоматические тесты не обращаются к внешнему API. Для проверки адаптера используем
настоящий Groq SDK с подставным HTTP-транспортом: авторизация, квота, таймаут, повреждённый
и обрезанный ответ. Отдельно проверяем входные данные, длины, цитаты, конфликт, экспорт
и сохранность существующих файлов. Временные файлы тестов находятся в `work/pytest-tmp`.

Реальные результаты и состояние проверки смотрите в `docs/verification.md`.
Отрицательные примеры описаны в `examples/README.md`.

## Структура

```text
src/product_card/   схемы, проверка фактов, промпт, API, сборка и экспорт
tests/             автоматические проверки
examples/          два товара, источники и ошибочные входы
outputs/           сохранённые результаты реальных запусков
docs/              решения, проверка и перечень требований
```

## Возможные улучшения

После получения товаров работодателя нужно повторить генерацию и сверку на них.
Дальше можно добавить проверку смысловой привязки отдельных утверждений к источнику,
более полную нормализацию единиц, набор предметных конфликтов и простую веб-форму.
Для текущего прототипа ручная проверка черновика остаётся обязательным этапом.
